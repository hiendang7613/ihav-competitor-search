Evidence labels: **admin** = admin statement; **default** = proposed default the admin let stand by saying "continue", not explicitly confirmed; **verified** = read in a local file on 2026-10-03; **proposed** = design choice made here, open to review; **unverified** = needs a live check.

## 1. Goal and decisions

Goal (admin): the user names a domain ("vector databases", "OCR APIs"). The plugin surveys the candidates or competitors in that domain and returns one table, ranked by the monthly visits of each candidate's website. Ships as a Claude Code and Codex plugin, GitHub-trend quality.

Admin-stated flow:

1. Round 1: one start prompt goes in parallel to many web AI chatbots (through `ihav-web-chat`). Each chatbot returns a table.
2. Synthesis: merge the tables into one, rank by visits from `ihav-web-visit-counter`.
3. Round 2..N: the prompt carries the synthesis table. Each chatbot returns only new candidates, never old ones. Merge again and re-rank.
4. Each round extends rows and also columns.
5. Final round: the agent verifies the synthesis table and fills missing data.
6. Default: 2 rounds.

| ID | Decision | Status |
|---|---|---|
| Q1 | A candidate is one product or service. Visits are counted on its official homepage domain. | default |
| Q2 | Candidates that share a domain use their subdomain or own domain when the counter has a number. Otherwise flag `shared_domain` and rank them after candidates with their own number. | default |
| Q3 | Order: `estimate` by visits desc, then `rank_only` by Tranco rank, then no data. | default |
| Q4 | Check for the child plugins; if missing, show the exact install command, ask the user once, then run it. Mechanism unverified (section 7). | default |
| Q5 | Default providers: ChatGPT, Gemini, Perplexity. `--providers a,b,c` or `--providers all`. | default |
| Q6 | Fixed core columns plus up to K new columns per round proposed by chatbots; the agent merges and names them. | default |
| Q7 | Default run: round 1, round 2, then verification. `--rounds N`, `--no-verify`. | default |
| Q8 | Verification opens official pages. Every filled cell keeps URL, date and method. No value from model memory. | default |
| Q9 | Outputs `table.md`, `table.csv`, one shareable `report.html`, same style family as ihav-leaderboards. | default |

Non-goals for v0: paid data sources, API keys, bypassing logins or bot walls, a hosted service, scoring candidate quality (ranking is by visits only).

## 2. Pipeline

```
domain prompt
  -> preview       show providers and exact outbound fields; one opt-in (2.0)
  -> R1 ask        start prompt to N chatbots (ihav-web-chat), JSON tables back
  -> R1 merge      parse, dedupe, column registry, mentioned_by
  -> R1 check      confirm each new candidate's official homepage and lookup host (2.2b)
  -> R1 rank       visits per lookup host (ihav-web-visit-counter); provisional rank
  -> R2 ask        prompt + current table: "only new candidates" + "up to K new columns"
  -> R2 merge / check / rank
  -> ... Rn        until --rounds N, or a round adds no candidate and no accepted column
  -> V verify      agent checks rows on official pages, fills gaps
  -> V rerank      re-query any host that verification changed; final rank
  -> render        md, csv, json, html, evidence export
```

Every stage writes to `./.ihav_space/ihav-competitor-search/runs/<run-id>/` (D-ea7f3bcd). Any stage resumes from its saved input, except that an external call with an uncertain outcome is reconciled first, never repeated blindly (2.1). A gap stays `null` with a reason.

### 2.0 Preview and consent (proposed, review F1)

- Before the first send, `survey` prints the provider list, the exact round-1 prompt and the field list that later rounds will add: candidate `name`, `homepage` and the values of accepted columns, all generated by chatbots or official pages. `--dry-run` stops here.
- One explicit opt-in covers all rounds of this run, for exactly these field kinds. If a later round would send anything outside them (for example user-supplied notes), the run stops and asks again.
- The user's domain text is sent verbatim to every selected provider. The preview says so. Nothing is sent before the opt-in is recorded in `request.json`.

### 2.1 Ask (proposed; child contract is a draft proposal in the ihav-web-chat design, not built or run)

- `ihav-web-chat run --to a,b,c --prompt-file F` writes the request, queues one job per provider and returns the run id at once (proposed in the ihav-web-chat draft design, section 4; not yet exposed by its package).
- Claude Code: the skill waits with `delivery wait --thread <session>` started through Bash `run_in_background`, from the main session, never a subagent (proposed in that draft, section 9). Codex follows that design's Codex callback path.
- Provider outcomes (child model, verified in `models.py`; review F5): the round waits until every provider is terminal (`completed`, `failed`, `timeout`, `login_required`, `human_verification_required`, `not_sent`, `sent_unknown`, `cancelled`) or the round deadline passes. Every provider status is stored in `children.json` and shown in the report. One provider failing never fails the round; the round is `partial`.
- `sent_unknown` means the send is unresolved. It is never retried automatically and never counted as "this provider found nothing". A round whose only non-completed providers are `sent_unknown` is `partial_unresolved`; the report lists it.
- Zero completed answers in round 1 stops the run with a clear message. Zero completed answers in a later round ends the loop and moves to verification, with the reason recorded.
- Launch idempotency (review F3): before calling `ihav-web-chat run`, the plugin writes `rounds/<n>/launch.json` with a stable request key (run id + round + prompt hash) and state `launching`. After the call returns, it records the child run id and state `launched`. On resume, a `launching` record without a child id is `unknown`: the plugin looks up the child run by the request key (requires a child-side lookup; open item O9) and, if it cannot reconcile, stops and asks. It never launches the round again on its own.
- Bound: ihav-web-chat v0 is macOS-only; its proposed first milestone is ChatGPT, Gemini and Perplexity (draft, not built). `--providers all` means every provider the installed ihav-web-chat supports.
- Dependency gate (admin R1, 2026-10-03 16:57): before round 1 the plugin checks that the installed `ihav-web-chat` exposes `run`, `status` and `delivery wait/read`, and lists its supported providers. If the check fails, the run stops with the exact missing command and the install step; it never falls back to model memory. Build of this stage waits until ihav-web-chat ships that CLI.
- After installing any child plugin, the run stops and tells the user to restart the host, as the visit-counter README requires (review F4). `resume` re-runs the gate first. The gate reads a versioned capability response from the child (`doctor --json` or equivalent: version, commands, supported providers); `--providers all` uses that list. The exact child command is open item O9.
- This plugin stores only child run IDs and the parsed answers it needs, not copies of ihav-web-chat run folders.

Prompt shape (proposed):

- Round 1: domain, what counts as a candidate (Q1), up to `--max-new` candidates (default 30, proposed), the core columns, and up to K proposed extra columns (default K = 5, proposed). The answer must be one fenced JSON object of this shape (review F12):

```json
{
  "columns": [
    {"key": "price_per_1k_pages", "label": "Price per 1,000 pages", "type": "number", "unit": "USD", "meaning": "list price for 1,000 pages, cheapest public plan"}
  ],
  "candidates": [
    {"name": "Example OCR", "homepage": "https://ocr.example.com", "values": {"category": "API", "price_per_1k_pages": 1.5}}
  ]
}
```

Fenced JSON keeps parsing deterministic, as in the ihav-leaderboards S1 proposal.
- Round n >= 2: the same, plus the current table as compact JSON (name, homepage and current columns only), the instruction "return only candidates not in this table", and "propose up to K columns not in this list, and give their values for your new candidates".

### 2.2 Merge (proposed)

- Parse each fenced JSON answer. An unparseable answer is kept raw, marked `parse_failed`, and reported.
- Candidate identity (review F6): product name plus a product-specific URL. Normalization first (case, punctuation, vendor prefix, "API"/"app" suffixes), then the LLM decides only the leftovers. A shared host alone never merges two candidates; two products on one vendor domain stay separate. Ambiguous matches stay unmerged and are listed in the report. This borrows the ihav-leaderboards S5 idea, which is itself a proposal.
- The traffic lookup host is a separate field (`lookup_host`), normalized the way the counter does it (strip leading `www.`, keep other subdomains). It is used only for visits and `shared_domain` grouping, never for identity.
- Chatbots will return old candidates despite the instruction. Repeats are merged, not counted as new, and add the provider to `mentioned_by`.
- `mentioned_by`: list of providers and rounds that named the candidate. Shown as a column; not used for ranking.
- Column registry (S6b idea from ihav-leaderboards, a proposal there): each column has `key`, `label`, `meaning`, `type` (`number`, `bool`, `category`, `text`, `url`), `unit`, `added_in_round`, `proposed_by` (list of provider and round).
- Column merge rule (review F7): two proposals merge only when meaning, type and canonical unit match, or a documented conversion exists (for example EUR to USD at a recorded rate and date). Otherwise they stay separate keys, even with the same label. Each value keeps its raw value, raw unit and source. A value whose type does not fit the column is kept raw and flagged `type_mismatch`.
- Column budget (review F8): at most K = 5 accepted new columns per round and at most 25 columns in total (core included), proposed defaults.
- Core columns (fixed, proposed): `name`, `homepage`, `domain`, `category`, `description`, `pricing_model`, `free_tier`, `open_source`, `founded`, `headquarters`.
- New columns leave older candidates `null`. Backfill happens in the verification round (section 2.4), not in later chatbot rounds, so "only new candidates" stays a simple instruction.
- Every cell keeps its source: `chatbot:<provider>:r<n>` until verified.
- Loop stop rule (review F8): the loop ends at `--rounds N`, or earlier when a round adds no new candidate and no accepted column.

### 2.2b Homepage check (proposed, review F2)

- Before any visit lookup, each new candidate gets one ordinary GET of its `homepage`. The agent confirms the page is live and names the product. If not, it searches the product's official site once with the host's web tools. The confirmed URL sets `homepage` and `lookup_host`; the check records URL, date and result.
- A candidate whose homepage cannot be confirmed keeps `homepage_status: unconfirmed` and is not looked up (sort group `not_looked_up`, reason recorded). No bypass of logins or bot walls.

### 2.3 Rank (proposed against the visit-counter contract, verified in its README and docs/how-it-works.md)

- Input per candidate: `lookup_host` from the confirmed homepage (2.2b). The counter keeps subdomains other than a leading `www.`, and does not guess a public-suffix boundary (verified). This makes Q2 workable for products on their own subdomain.
- One counter lookup per `lookup_host`, deduped within the run. The counter caches results 24 hours and sends one request per lookup, with no batch mode (verified).
- Result kinds (verified): `estimate` (modelled `monthly_visits`, `analyzed_at`, source link) or `rank_only` (Tranco rank, `monthly_visits: null`). Exit codes: `0` result, `2` no data, `4` blocked or rate-limited (source stops, no retry), `5` network or cache failure, `64` bad input.
- Sort key (Q3, review F9), groups in this order:
  1. `estimate`, by `monthly_visits` desc
  2. `rank_only`, by Tranco rank asc
  3. `no_data` (counter exit `2`)
  4. `lookup_failed` (exit `4` blocked, exit `5` network or cache, exit `64` bad input)
  5. `not_looked_up` (over the cap, homepage unconfirmed, or stopped after a block)
  Inside each group, ties by name. Groups 3 to 5 get no traffic rank number; the table shows `lookup_status` and `rank_basis` for every row.
- `shared_domain` (Q2): when two or more candidates resolve to the same `lookup_host`, each keeps the host number but carries `shared_domain: true` and sorts after the candidates with their own number, inside its group.
- Exit `4` on any lookup: stop further lookups for this run, keep the results so far, mark the rest `visits_unavailable: blocked`, and report it. No retry.
- Candidate cap: at most 100 visit lookups per run by default (`--max-lookups`, proposed). The source terms allow only reasonable, low-volume automated use (verified, visit-counter README). Candidates above the cap stay in the table, marked `not_looked_up`.
- Source terms (review F10, unresolved): the WebTrafficChecker terms also prohibit using its API to build a substantially similar or competing service, and give no numeric limit (verified, visit-counter README). The cap, cache and stop-on-block rules reduce load; they do not settle whether this plugin's use is allowed. Admin resolved O7 (P-ecd9ba1b): proceed, stop on block, state the risk in README.
- Each row shows visits with `kind`, `analyzed_at` and source, as the counter does. Visits are a modelled estimate, not owner analytics; the report says so.

### 2.4 Verify (proposed)

- Runs after the last chatbot round unless `--no-verify` (Q7).
- For each candidate, the agent opens the official homepage and the pages it needs (pricing, docs, about) with the host's ordinary web fetch or browser tools. No bypass of logins or bot walls.
- For each cell: confirm, correct or fill. Every value records `source_url`, `fetched_at` and `method` (`page`, `chatbot`). The agent never fills a value from memory. A cell it cannot check stays as given or `null`, with `verification: unverified` and a reason.
- Row-level `verification_status`: `verified` (all filled cells checked), `partial`, `unverified`, `dead_homepage`. Shown as its own column, separate from the rank (CODEX_01 review note, 2026-10-03).
- A dead homepage or a candidate that is not in the domain is flagged, not deleted.
- Bound: verification cost grows with rows times columns. Default cap: verify the top 50 rows of the provisional rank (`--verify-top`, proposed); the rest stay `unverified`.
- Rerank (review F2): if verification changes a candidate's `homepage` or `lookup_host`, the plugin looks up the new host (within the lookup cap) and recomputes the final rank. If the rerank moves an unverified row into the top 50, the report lists it as "entered top 50 after rerank, not verified"; the plugin does not start another verification pass on its own.

## 3. Outputs (Q9)

Run folder:

```
./.ihav_space/ihav-competitor-search/runs/<run-id>/
  request.json            domain, options, providers, schema version
  rounds/<n>/prompt.md
  rounds/<n>/answers/<provider>.json   parsed answer, or raw with parse_failed
  rounds/<n>/children.json             ihav-web-chat run id and per-provider status
  synthesis/<n>.json      table after round n: rows, column registry, mentioned_by
  visits.json             counter result per domain, with kind, source, analyzed_at
  verification/<slug>.json  per-candidate checks with source URLs
  launch.json per round   request key, state, child run id (2.1)
  table.json  table.md  table.csv  evidence.csv  report.html
```

Per-cell evidence (review F11): `table.json` stores each cell as `{value, raw_value, raw_unit, source_url, fetched_at, method, verification}`. `evidence.csv` has one row per candidate and column with the same fields, keyed by `candidate_id` and `column_key`. `table.csv` stays one clean row per candidate plus `lookup_status`, `rank_basis` and `verification_status`. In `table.md` and `report.html`, each verified cell links to its source and shows date and method on hover or in a footnote. Source presence and verification state are separate fields.

`report.html` is one static file with inline data: ranked table (sortable, badges for bool and category columns), visits bar chart with the `kind` encoded, `mentioned_by` and verification badges, and a run summary (rounds, providers, new candidates per round, columns added per round, lookups skipped). Chart work follows the dataviz guidance at build time.

The plugin warns, and does not edit, when `.ihav_space/` is missing from the calling project's `.gitignore`.

## 4. CLI (proposed)

| Command | Effect |
|---|---|
| `survey "<domain>" [--rounds 2] [--providers ...] [--max-new 30] [--max-lookups 100] [--verify-top 50] [--no-verify]` | Start a run; print run id and next step |
| `status <run-id>` | Read stage states; no network |
| `resume <run-id>` | Continue from the last saved stage |
| `render <run-id>` | Rebuild md, csv, html from saved JSON |

The ask and verify stages need the host agent (chatbot callbacks, LLM dedupe, page reading). Merge, rank and render are deterministic Python and testable offline.
